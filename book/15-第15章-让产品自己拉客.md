# 第 15 章 让产品自己拉客：免费工具、试用、开放接口

以前拿到一个客户，第一步总是人先动：销售打电话、投手投广告、写手发内容，客户是被推着走的。现在有一批客户是自己找上来的——他先用你的计算器把自己的账算了一遍，或者在试用里跑完了一次真活儿，用顺了才回头问一句"你们公司是哪家"。这种客户开口就是具体问题，没人跟你客套，也没人从头听你介绍公司。

客户可能先用了你的东西才认识你这家公司。所以这章给你 5 个办法，不做人的动作也带来线索。

---

## 办法 1：做个小工具，让人先用上再留联系方式

**做什么**：把你最常被问的那一个问题做成一个免费小工具，让客户先拿到结果，再谈留联系方式。

**怎么做**

1. 从销售和客服的聊天记录里，挑**被问得最多、答案又最标准化**的那一个问题——报价估算、单位换算、额度测算、合规体检，选一个。问的人多，说明搜的人也多，这个工具的入口天然是开着的。
2. 小工具只干一件事：输入三四项，输出一个数字或一份清单。输入项越少越好，每多一项都要掉一批人【本书判断】。能默认的先默认，能让客户选的就别让他填。
3. 顺序定死：填输入 → 看到结果 → 想存下结果或看下一层 → 这里才弹留资框。要联系方式这一步放在结果**之后**，不在前面。
4. 给一个能带走的产出：一份 PDF、一张图、一条可复制的结论。愿意存下来的人，才是真有兴趣的人。
5. 每月只看两个数：有多少人用了，用完的人里有多少留了联系方式。第二个数才是这个钩子的成绩；第一个数好看但第二个数不动，问题出在结果那一屏。
6. 工具放在独立域名或者独立路径上，别塞进官网首页的弹窗里。它要干的活儿是被人搜到、被人转发，弹窗两件都做不到【本书判断】。

**例子**：暂无公开可核的案例。

**别踩的坑**：把工具做成缩水版的产品介绍页，输入框只用来收集资料——客户填到一半发现看不到结果，就走了。

## 办法 2：把接口开放出去，让你的能力能被机器调用

**做什么**：把你的核心能力按公开标准包成接口，让别人的 AI 能直接调用它，调用方就成了你的一条线索来源。

**怎么做**

1. 按公开标准想清楚你的能力该暴露成什么。以 MCP 为例，规范把角色分成 Hosts（发起连接的 AI 应用）、Clients（宿主应用里的连接器）、Servers（提供上下文和能力的服务），服务对外给三类东西：Resources（数据和上下文）、Prompts（模板化消息与工作流）、Tools（可执行的函数）【官方口径】。你要回答的问题是"我的能力包成哪个工具函数、参数怎么填、返回什么"，不是"我的网页怎么排版"。
2. 接口说明书按"给机器看"的标准写：能力名、每个参数的含义和取值范围、返回字段、出错时的提示。调用方的 AI 是照着这份说明书决定用不用你的，说明书里没写的用法，它不会自己猜。
3. 接通一次就够。文档把这类协议比作 AI 应用的 USB-C 口——接一次，能被多个客户端用【官方口径】。所以标准要选主流的那个，不要自己另立一套。
4. 先开放只读的那部分。查询、计算、比对这类不动对方数据的能力，授权门槛低、容易先被接上；写入类的能力往后放，客户那边也要多一点时间才敢给你权限。
5. 在服务名和返回值里留一个可识别的身份。被调用的时候你不知道对面是谁，但对方的人和后面的账单要能认出你。
6. 版本号留在接口地址里，旧版本留一段过渡期。接口一改，已经接上的人会直接坏掉，而你不会收到任何投诉——他们只是不再调用了。

**例子**：MCP 规范当前版本是 2026-07-28，规范把协议定义为 AI 应用与外部数据源、工具之间的开放标准，消息用 JSON-RPC 传，服务对外的三类能力是数据、提示模板和工具函数【官方口径】。入门文档把它比作"AI 应用的 USB-C 接口"，并列出了已经支持它的客户端——Claude、ChatGPT、Visual Studio Code、Cursor 等，写一次可以接到多处【官方口径】。

**别踩的坑**：把"开放接口"理解成"挂一份 API 文档"。文档放在那儿没人读，能被调起来才算数。

## 办法 3：把服务发布进官方目录，让 Agent 自己找到你

**做什么**：把服务发布到官方注册表和平台应用目录里，让买家的 Agent 和平台在选供应商时把你捞出来。

**怎么做**

1. 分清楚两类目录。一类是**协议级注册表**（比如 MCP 的官方注册表），发布的是元数据，供客户端和聚合器发现有哪些服务可用；另一类是**平台应用目录**（支付平台、协同办公平台的应用市场），收录的是一个个应用条目，客户会在那里挑。两类都要进，它们的作用不一样。
2. 备齐发布用的元数据：服务的唯一名字、安装位置（包名或远端地址）、启动与配置说明（命令行参数、环境变量）、能力描述。这几项是登记时绕不过去的字段，缺一项就发不上去。
3. 名字取成反向域名的格式，并且要能证明这个命名空间是你的——用你的域名或代码托管账号验证归属。名字和归属对得上，审核才过得去；对不上，等于替别人占位。
4. 发布的门槛通常是"安装方式公开可装"或者"服务本身公开可访问"。只对内部开放的私有服务，一般不在收录范围里。
5. 发布完不要收工：**下游的聚合器和市场才是客户真正会看到的地方**。注册表给的是一份不带排序的元数据，市场会再加评分和推荐，所以主流的几个市场要挨个补一遍材料。
6. 目录条目里的介绍，用客户真会敲进去的话写，不用你们内部那套说法。这一段写得好不好，直接决定你会不会出现在那一次搜索里。

**例子**：MCP 的官方注册表是那份集中目录，公开可访问的服务可以把元数据发布进去，客户端和聚合器通过它的接口发现有哪些服务可用【官方口径】。Stripe 的 Directory 文档写得最直白：它让开发者和 AI agent 找到某个任务最合适的外部服务商，索引的东西包括应用市场上架的应用、可以一条命令开通的服务商、支持按次付费的接口目录，搜索结果里带服务商标识和接口地址这些结构化字段【官方口径】；文档还给了写法——简介要用客户真会敲进去的词，像"帮自由职业者开发票、更快拿到钱"，比"下一代财务运营平台"更容易被搜到；多用完整短语，别把词拆开散着放；显示名和账号名要跟客户认识你时叫的名字一致，不然有人直接搜你的名字也搜不到你【官方口径】。

**别踩的坑**：以为在注册表里挂上名字就等于有线索。目录只给你一次被搜到的机会，能不能被选中，看的是条目里的说明和目录外面的评价【本书判断】。

## 办法 4：把试用和免费额度的边界写死

**做什么**：免费给到什么程度、什么时候开始要钱、额度怎么算，全部提前写死，让试用期自己去筛人。

**怎么做**

1. 免费只给一个维度：要么给时间，要么给次数。两个一起给，客户算不明白自己还剩多少，用起来就缩手缩脚。
2. 把"用完会怎么样"写在第一次使用之前：还剩多少额度、用完是停住还是自动扣费、扣多少钱。客户最怕的是试用快结束时收到一张没预期的账单，那种纠纷比没转化更贵【本书判断】。
3. 让客户在试用里干成一件真事，而不是把功能都点一遍。判断标准是"他有没有拿自己的数据跑过一次"——这一步过了，后面才谈得上付费。
4. 分两条线跟进。用过但没到额度的，和额度用完停住的，发的东西完全不一样：前一条缺的是用起来的理由，后一条缺的是一笔预算。
5. 试用期里把开通、跳出、用到额度这几个节点记下来，看人卡在哪一屏。卡点在调整产品的时候，比一个笼统的转化率好用。
6. 免费用法和优惠政策收敛到一处。同一家公司摆出两套试用规则，客户会截图比价，销售也解释不清哪个才算数。

**例子**：暂无公开可核的案例。

**别踩的坑**：把免费额度设成"刚好不够干成一件事"。客户试完只会记住一件事——你们这儿做不成事。

## 办法 5：把工具的结果页做成留资页

**做什么**：让工具算出来的那份结果自己去找下一个客户，顺带把新的来客接住。

**怎么做**

1. 结果页给三样东西：结论、依据、下一步。依据就是"这个数字是怎么算出来的"，能把算法和参数区间写清楚的工具，被转发的次数最多【本书判断】。
2. 结果做成能带走的样式：一条可复制的结论、一张图、一份 PDF。客户带走的时候，他自己的输入和你的名字一起被带走。
3. 让结果页能被搜到、能被 AI 读到。给常见的输入组合各生成一个静态页面，标题写客户会搜的那个问题，正文写清输入条件和算出来的结论。别人搜同样的条件时，搜到的就是你这一页，而不是别人的工具。
4. 转发路径上留一个入口：收到图或链接的人点开，能用自己的条件再算一遍。第二次算的那个人，就是你新拿到的一条线索。
5. 每个结果页底部留一个"要看详细版"的位置，联系方式只在那一处要一次，别在页面里到处伸手。
6. 结果页上别放一堆导航。客户是带着一个具体问题进来的，这一页只回答那一个问题，出口只留一个。

**例子**：暂无公开可核的案例。

**别踩的坑**：结果页只有一句"恭喜完成测评"和一个二维码。客户拿不到能带走的东西，这一页就白做了。

## 本章注意

- 这一章**不引用任何试用或免费工具的转化百分比**。素材里能找到的这类数字（免费试用转付费率之类）全部出自没有原始来源的聚合博客，一个都不用，所以办法 1、4、5 只给做法、不给效果。想知道有没有用，照第 20 章那样自己记账。
- 国内平台的开放能力目录（微信小程序、飞书应用市场、钉钉开放平台、扣子商店）这次没有采到，OpenAI 帮助中心的《Build with the Apps SDK》也没有采到（curl 返回 403）。所以办法 3 的做法以 MCP 与 Stripe 两家公开文档为准，换到别家平台要按各家自己的收录规则重走一遍。
- 工具钩子的设计目前没有权威口径。办法 1 和办法 5 是按可操作的做法写的，不是标准答案。
- 办法 2、3 引的都是官方文档，讲的是**机制**，不是效果承诺。它说的是怎么被调用、怎么被收录，没说做了会带来多少线索。
- 把能力开放出去之前先想清授权边界。MCP 规范把用户同意、数据访问控制和工具调用前的授权写成实现方必须处理的原则，不是可选项【官方口径】——开接口这件事在合规上是有代价的。
